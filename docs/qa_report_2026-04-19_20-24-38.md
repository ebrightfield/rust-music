### Warnings

#### W1. Production `unwrap()` on `iter().min()/max()` with only logical — not type-enforced — non-empty guards
**Files:**
- `src/layout/beam.rs:55–56` (`auto_stem_direction`)
- `src/layout/beam.rs:180, 183` (beam layout: `natural_tips.last().unwrap()`, `notes.last().unwrap()`, `notes[0]`)
- `src/layout/stem.rs:38–39` (`auto_stem_direction_chord`)
- `src/layout/chord.rs:140–141` (`chord_extent`)
- `src/layout/tuplet.rs:132, 138`

Each is preceded by an `if empty { return … }` early-return, so the invariant holds today, but the invariants are a few lines away from the panic site and tightly coupled. A small local refactor (e.g., `let (min, max) = slice.iter().minmax()?;` via itertools, or destructuring via `match slice { [] => …, [first, rest @ ..] => … }`) would push the non-empty proof to the type level. **Warning-tier** rather than critical because the guards are present.

#### W2. Production `unwrap()` in `time_signature::number_to_digit_glyphs` without bounds check on input
`src/layout/time_signature.rs:50, 52` call `digit_glyph(tens).unwrap()` / `digit_glyph(ones).unwrap()`. `digit_glyph` returns `Option<Glyph>` for 0–9. The comment says "1–99" but the fn signature takes `u8`, so a caller passing `n >= 100` would compute `tens = n/10 >= 10` and panic. Either change input type to a bounded newtype, or return `Result<Vec<Glyph>, _>` and propagate.

#### W3. `layout::rest::rest_glyph(d).unwrap()` is protected by an `assert` that's off-by-one-plausible
`src/layout/rest.rs:146` — the surrounding context implicitly assumes `d <= 7`. Same shape as W2: a bounded integer type or explicit `?` would type-prove the invariant.

#### W4. `layout::barline.rs:282` — `bl.dots.unwrap()` after constructing a non-repeat barline
The unwrap is in a test block inside the module but the `cfg(test)` guard wasn't matched by the conservative scanner; worth confirming. If it's in production code, document the repeat-style precondition.

#### W5. `score::ScoreBuilder::render_svg` calls `.expect("font rendering should not fail for valid input")`
`src/score.rs:612`. This is the advertised "convenience" API — it **is** the primary entry point in the doc example (`lib.rs`) and every runnable example. The `try_render_svg` sibling exists, but the panicking version is what users will reach for. Consider whether font errors can actually occur for the bundled Bravura font given a valid `ScoreBuilder` state (likely no, since all glyph lookups go through names guaranteed by `smufl` crate + Bravura metadata). If truly unreachable, document *why* the expect is safe; otherwise return `Result` and let callers `.unwrap()` explicitly.

#### W6. Font loading uses `expect()` at module boundary
`src/font/mod.rs:23` — `bravura_font()` panics with `"bundled Bravura font should be valid"`. This is reasonable (the font is `include_bytes!`'d and validated by tests), but it means any `bravura_font()` caller may panic at startup if the bundled asset is ever corrupted. Acceptable — flagging for completeness since the public API has a non-`Result` construction path that can panic.

#### W7. `write!(self.path, …).unwrap()` on a `String` Writer
`src/font/glyph_outline.rs:39, 43, 47–55, 62–69`. Writing to a `String` via `fmt::Write` only fails under OOM, which is typically treated as unrecoverable — but `write!(s, …).unwrap()` is idiomatically replaced with `let _ = write!(…);` or just delegating to a formatter. Cosmetic; flagging under safety bucket because the pattern is the usual "unwrap on impossible error" smell.

#### W8. Clippy: `identity_op` with a stale inline comment
`src/layout/tuplet.rs:253` — `let bottom_y = (8 - 0) as f64 * HS; // 1000.0`. The `- 0` is cruft and the comment is a hardcoded calibration value that may not match `HS`. Worth auditing whether the literal `8` is the right staff-position constant or should be `BOTTOM_LINE`/`STANDARD_LINE_COUNT * 2`.

#### W9. Clippy: `useless_format` in dot renderer
`src/render/dot_renderer.rs:111` — `let translate = format!("translate(");`. Minor.

#### W10. Clippy: `clone_on_copy` for `Pitch` at 5 sites
`src/score.rs:1294, 1534, 1545, 1923, 1924`. `Pitch` is `Copy`; `.clone()` is dead code.

#### W11. Clippy: redundant closures in example
`music-engraver/examples/key_signatures.rs:41, 42, 46, 47`. `.map(|n| KeySignature::Sharps(n))` → `.map(KeySignature::Sharps)`.

#### W12. Centralized error type missing
The crate has no `src/error.rs`. Every fallible function returns `Result<_, FontError>`, where `FontError` lives in `src/font/music_font.rs`. Anything that isn't a font-glyph lookup (e.g., layout preconditions, invalid input ranges, empty scores) has no home to report errors and currently either panics or silently no-ops (see W2–W4). Consider a top-level `Error` enum (thiserror is already a dependency) so that layout-level failures become typed instead of `unwrap()`-panics.

#### W13. `src/score.rs` is 3,272 lines — split point
This is the single biggest file in the crate. It holds:
- `ScoreBuilder` + fluent API (~560 LOC)
- `ScoreEvent` enum + conversion (`convert_event`, `convert_event_tracked`) (~400 LOC)
- Large test module (~1,800+ LOC).

Splits worth considering:
- Move the `convert_event*` logic + `ScoreEvent` → `score/event.rs`.
- Move test helpers + tests into `score/tests.rs` (or a sibling `tests/` file).
- Keep `ScoreBuilder` as the module root.

#### W14. `src/render/measure_renderer.rs` is 2,105 lines
Contains `draw_note_event`, `draw_chord_event`, `draw_beam_group_event`, `draw_tuplet_group_event`, `draw_rest_event`, `draw_measure`, plus a large test module. Sub-modules (`note`, `chord`, `group`, `tuplet`) inside a `measure_renderer/` folder would make dispatch explicit and shrink each file to ~300 LOC of core logic.

#### W15. `src/render/page_renderer.rs` is 1,438 lines; `system_renderer.rs` 1,200
Both mix: (a) primary layout pass, (b) within-system tie/slur/hairpin collection, and (c) cross-system tie/slur/hairpin resolution. Each cross-system feature (ties, slurs, hairpins) has three near-identical groupings: `UnresolvedX` struct, `find_unresolved_x()`, `find_incoming_x_targets()`, `draw_cross_system_x()`. See DRY section (I2) below — but even without extraction, moving each cross-spanning concern into `page_renderer/tie.rs`, `slur.rs`, `hairpin.rs` would aid navigation.

#### W16. `layout::measure::MeasureLayoutConfig` and `NoteEvent`/`ChordEvent` are modifier-grab-bags
`src/layout/measure.rs:764` total lines; `NoteEvent` has `tie_forward: bool`, `dynamic: Option<Dynamic>`, `slur_start: bool`, `slur_end: bool`, `hairpin_start: Option<HairpinType>`, `hairpin_end: bool`, `rehearsal_mark: Option<…>`, `tempo_mark: Option<TempoMark>`, `expression: Option<String>`. Cross-cutting field counts (grep): 404 occurrences in `score.rs`, 114 in `measure.rs`, 398 in `measure_renderer.rs`. Every new annotation adds a field in 10+ construction sites (as the log entries repeatedly note). This is a strong signal that a `NoteAnnotations` struct (or `Vec<NoteAnnotation>` sum type) would collapse the per-field plumbing into a single generic pass-through.

#### W17. `cargo clippy --all-targets` warnings contradict progress-log claim
`ENGRAVER-PROGRESS.md` states "0 warnings" after each run. That holds for `cargo clippy -p music-engraver` on the lib only. The 15 warnings above surface once tests/examples are included. Fix the log claim, or tighten the lint gate (e.g. a `#![deny(warnings)]` in tests/examples or run with `--all-targets` in CI).

#### I2. DRY — cross-system span rendering triplicated
In `page_renderer.rs`, ties, slurs, and hairpins each implement structurally identical span-resolution:

- `UnresolvedTie` / `UnresolvedSlur` / `UnresolvedHairpin`
- `find_unresolved_ties()` / `find_unresolved_slurs()` / `find_unresolved_hairpins()`
- `find_incoming_tie_targets()` / `find_incoming_slur_targets()` / `find_incoming_hairpin_targets()`
- `draw_cross_system_ties()` / `draw_cross_system_slurs()` / `draw_cross_system_hairpins()`

A generic `CrossSystemSpan<Kind>` trait (associated types: `Layout`, `Info`, half-layout fns) would unify all three. Caveat: the "extract macro/trait only if genuinely cleaner" rule applies — the three have enough asymmetry (slurs use bezier, hairpins use lines, ties use lens) that the unified form might be worse. Flagging as an option, not a required cleanup.

#### I3. DRY — `ScoreEvent → MeasureEvent` conversion duplicated across `convert_event` and `convert_event_tracked`
`src/score.rs:618` and `src/score.rs:746`. The two functions differ only in whether they consult `within_measure_accidentals`. Consider a single function `convert_event(tracked: Option<&mut AccidentalTracker>, …)`, or a trait-based "accidental resolver" with two impls (stateless / stateful).

## Recommendations

Ordered by effort-to-value ratio (high value, low effort first).

1. **Clippy cleanup pass (30 min).** Fix the 15 warnings (W8–W11). Re-establish the "0 warnings" invariant and tighten the progress-log claim to match `--all-targets`.
2. **Fix `#[must_use]` on builder methods (15 min).** High-value signal for users who forget to chain `.render_svg()`.
3. **Add a central `Error` enum (1–2 h).** Room to grow beyond `FontError` without refactoring later. `thiserror` is already pulled in.
4. **Introduce a bounded `TimeSigDigit` type or `Result`-return on `digit_glyph`** (W2, 1 h). Closes the one panic path that depends on caller discipline.
5. **Collapse `NoteEvent`/`ChordEvent` modifiers into a `NoteAnnotations` struct (2–4 h).** The progress log documents that every new annotation touches 10+ sites. A single struct behind one field would eliminate this tax going forward.
6. **Split `score.rs` and `measure_renderer.rs` (4–6 h).** Mechanical, low-risk, but will reduce future merge friction and aid navigation. `render/page_renderer.rs` and `system_renderer.rs` are also candidates.
7. **Consider deduplicating cross-system span resolution** (I2). Only if it genuinely reads better — the three concrete span kinds are different enough that a generic trait may not help. Defer until a fourth span kind (e.g., cresc-hairpin-over-pedal) lands.
8. **Add `#![deny(warnings)]` to CI or the lib** after cleanup pass.
9. **Post-v1 backlog continues as-is.** The architecture has held up well through ten post-v1 features (chord ties, cross-system ties, dynamics, tuplet brackets, slurs, cross-system slurs, hairpins, cross-system hairpins, rehearsal marks, tempo marks, expression text). Abstraction boundaries between `layout/`, `render/`, and `score/` are intact.

No remediation code was written. All findings are documentation-only, per the audit contract.
